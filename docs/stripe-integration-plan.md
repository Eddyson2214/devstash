# Stripe Integration Plan — DevStash Pro

> Generated by `/research stripe-integration-research.md`. Documentation only — no source files were modified.

## 1. Current State Analysis

### 1.1 User model (`prisma/schema.prisma`)

```prisma
model User {
  id                   String  @id @default(cuid())
  ...
  isPro                Boolean @default(false)
  stripeCustomerId     String? @unique
  stripeSubscriptionId String? @unique
  ...
}
```

The billing fields already exist — no migration needed to *add* them. However, two gaps to plan around:

- **No subscription status/period tracking.** Only a single `isPro` boolean and `stripeSubscriptionId`. There's no `stripeCurrentPeriodEnd`, `stripePriceId`, or `subscriptionStatus` field, so today the schema can't distinguish "active", "past_due", "canceled-but-still-in-grace-period", etc. A migration adding these is recommended (see §2.1) so the webhook handler has somewhere to persist subscription lifecycle state, and so a canceled-but-not-yet-expired Pro user doesn't lose access early.
- **No billing interval stored.** `STRIPE_PRICE_ID_MONTHLY` / `STRIPE_PRICE_ID_YEARLY` already exist as env vars (see §1.4) but nothing on `User` records which one a subscriber is on. Useful for the settings page ("You're on the annual plan").

### 1.2 NextAuth v5 configuration (`src/auth.ts`, `src/auth.config.ts`)

- Split-file pattern: `auth.config.ts` holds edge-safe provider config (Credentials `authorize` is a no-op placeholder there), `auth.ts` has the real bcrypt-based `authorize` and is where the `session` callback lives.
- Session strategy is **JWT** (`session: { strategy: "jwt" }`), not database sessions.
- The `session` callback (`auth.ts:18-28`) already does a DB read on every session validation to hydrate `emailVerified`:

```typescript
async session({ session, token }) {
  if (token.sub) {
    session.user.id = token.sub;
    const user = await prisma.user.findUnique({
      where: { id: token.sub },
      select: { emailVerified: true },
    });
    session.user.emailVerified = user?.emailVerified ?? null;
  }
  return session;
},
```

  This is the established precedent for syncing DB state into the session on every request — `isPro` should be added to this **same** query (just extend the `select`) rather than adding a second DB round-trip or a separate `jwt` callback query. This directly resolves the ambiguity flagged in the research prompt's Notes section: the prompt suggested syncing `isPro` in the `jwt` callback, but this codebase's existing pattern already syncs derived DB state in the `session` callback instead, and there's no reason to duplicate the query in a second callback. One DB read per session validation, not two.
- `session.user` type is extended in `src/types/next-auth.d.ts` — `isPro` needs to be added there too.
- No `jwt` callback currently exists at all in `auth.ts` beyond what NextAuth's defaults provide; `token.sub` is populated automatically by NextAuth from the adapter user, so nothing needs to change on the JWT side to add `isPro`.

### 1.3 How user data is accessed

- Server components call `auth()` directly (e.g. `src/app/settings/page.tsx`, `src/app/dashboard/page.tsx`), then thread `session.user.id` into `src/lib/db/*.ts` query functions.
- Server Actions (`src/actions/*.ts`) all follow the identical guard:
  ```typescript
  const session = await auth();
  if (!session?.user?.id) {
    return { success: false, error: "Not authenticated" };
  }
  ```
- **No existing code reads `session.user.isPro` anywhere.** `isPro` is not currently checked in the client or server — confirmed via a codebase-wide search; the only references to `isPro` are the Prisma schema, `prisma/seed.ts`/`prisma/sampledata.ts`, `proxy.ts` is unrelated (auth-only, no Pro gating), and `context/project-overview.md`'s spec. This is a **greenfield feature gate** — nothing to migrate away from.
- Known pre-existing tech debt (unrelated to this feature but touches adjacent code): `getCollectionStats()` in `src/lib/db/collections.ts:281` still calls a hardcoded `getDemoUserId()` instead of taking a `userId` param (unlike `getItemStats(userId)` in `items.ts`, which was already fixed). If this plan's limit-checking logic calls `getCollectionStats()`, that call will silently check the **demo account's** collection count instead of the real signed-in user's — this bug should be fixed as a prerequisite, not worked around, since the fix is a one-line signature change matching the already-established `getItemStats` pattern.

### 1.4 Existing Stripe configuration

`.env` **already contains live Stripe test-mode configuration** — a Stripe account/products have already been set up outside this research task:

```
STRIPE_SECRET_KEY=sk_test_...

STRIPE_WEBHOOK_SECRET=          # empty — not yet configured
```

Per `project-overview.md`'s explicit **dev-mode note**: *"gate the plumbing (isPro checks, limits) but leave all features unlocked for every user so the full product can be tested end-to-end before billing goes live."* This plan follows that instruction — all gate checks should be implemented as real, callable logic, but not yet enforced as hard blocks in the UI/actions until the user explicitly flips them on post-billing-launch. Concretely: write the limit-check helpers and call sites, but log/no-op rather than reject, OR gate behind a feature flag (mirroring the existing `isEmailVerificationEnabled()` pattern in `src/lib/feature-flags.ts`) — recommend the latter, since it's the codebase's established convention for "plumbing exists, defaults to not blocking anyone."

### 2.2 Where item/collection counts are checked or could be checked

- `getItemStats(userId)` (`src/lib/db/items.ts:114`) already returns `{ total, favorites }` — the `total` count is exactly what a 50-item free-tier check needs. Already used by the dashboard's stats cards.
- `getCollectionStats()` (`src/lib/db/collections.ts:281`) returns `{ total, favorites }` similarly, but see §1.3's bug note — needs the `userId`-param fix first.
- The natural enforcement point is **`createItem`/`createCollection` in `src/actions/items.ts`/`collections.ts`**, right after the `auth()` guard and before the Zod validation, mirroring how every other precondition in these actions short-circuits with `{ success: false, error: ... }`. A limit check would call `getItemStats(session.user.id)` (or a new lighter-weight `prisma.item.count()` if fetching `favorites` too is wasteful — recommend a new `countItemsForUser(userId)` / `countCollectionsForUser(userId)` pair in the respective `db/*.ts` files, since existing `getItemStats`/`getCollectionStats` return more than needed and are used by dashboard-stats call sites that shouldn't be coupled to the gating check).
- No UI currently shows "N/50 items used" anywhere — would need a new small component, likely placed in `/settings` near the (currently nonexistent) billing section, or as a subtle indicator in `Topbar`/`AppSidebar`.

## 3. API & Webhook Patterns

### 3.1 API route structure

Every route under `src/app/api/**/*.ts` follows the same shape (`upload/route.ts`, `register/route.ts` are the clearest examples):

```typescript
export async function POST(request: Request) {
  const session = await auth();
  if (!session?.user?.id) {
    return NextResponse.json({ error: "Not authenticated" }, { status: 401 });
  }
  // ...validate via zod or manual checks, NextResponse.json({error}, {status}) on failure...
  // ...do the work...
  return NextResponse.json({ ...result });
}
```

A Stripe **webhook** route is the one exception to "always check `auth()`" — it's authenticated via Stripe's signature header instead, not a user session, and must read the **raw** request body (Next.js route handlers support this via `request.text()`, not `request.json()`, since Stripe's signature verification needs the exact raw bytes).

### 3.2 Server Action error handling pattern

Every `"use server"` action in `src/actions/*.ts` returns a discriminated union:

```typescript
Promise<{ success: true; data: T } | { success: false; error: string }>
```

with a `try/catch` only where the underlying call can throw unexpectedly (most just let Prisma/Zod errors propagate since `.safeParse` + null-check patterns cover expected failure modes). Stripe SDK calls (`stripe.checkout.sessions.create`, `stripe.billingPortal.sessions.create`) **can** throw (network errors, invalid params) — these two new actions should wrap the Stripe call in `try/catch` and return `{ success: false, error: "..." }` on failure, matching `coding-standards.md`'s "Use try/catch in Server Actions" rule.

### 3.3 Environment variable patterns

- Simple `process.env.X` reads, no validation library (no `t3-env` or `zod`-validated env schema in this codebase).
- Optional/feature-flag-style vars follow the `EMAIL_VERIFICATION_ENABLED` pattern: a dedicated function in `src/lib/feature-flags.ts` (`isEmailVerificationEnabled()`), not inline `process.env` checks scattered across call sites.
- Service clients that need env vars are constructed once at module scope and exported (e.g. `src/lib/rate-limit.ts`'s `redis`/limiter singletons, `src/lib/prisma.ts`'s `prisma` singleton). A new `src/lib/stripe.ts` should follow this exact shape — a single exported `stripe` client instance, not re-instantiated per call.
- Secrets belonging to server-only integrations (Resend, R2, Upstash, and now Stripe) are never exposed to the client — only `STRIPE_PUBLISHABLE_KEY` is safe to ship to the browser, and per Next.js convention it should be renamed `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` when read from client code (the current `.env` key `STRIPE_PUBLISHABLE_KEY` has no `NEXT_PUBLIC_` prefix — needs to be added, or dual-defined, before any client component reads it directly. Note Stripe Checkout is redirect-based, so the publishable key may not even be needed client-side if using `stripe.checkout.sessions.create` + `redirect: "if_required"`/URL redirect rather than `stripe.js`'s embedded/redirectToCheckout flow — recommend the server-redirect approach specifically to avoid needing the publishable key in the browser at all).

**`src/app/api/webhooks/stripe/route.ts`** — the one route that deliberately does NOT call `auth()`:
```typescript
export async function POST(request: Request) {
  const body = await request.text();
  const signature = request.headers.get("stripe-signature");
  if (!signature) return NextResponse.json({ error: "Missing signature" }, { status: 400 });

  let event: Stripe.Event;
  try {
    event = stripe.webhooks.constructEvent(body, signature, process.env.STRIPE_WEBHOOK_SECRET!);
  } catch {
    return NextResponse.json({ error: "Invalid signature" }, { status: 400 });
  }

  switch (event.type) {
    case "checkout.session.completed":
    case "customer.subscription.created":
    case "customer.subscription.updated":
    case "customer.subscription.deleted":
      // resolve customer -> userId, call syncSubscriptionFromStripe(...)
      break;
  }

  return NextResponse.json({ received: true });
}
```
Handle all four events through one shared "sync subscription state" code path (fetch the subscription via `event.data.object`, derive `isPro` from `status === "active" || status === "trialing"`) rather than bespoke logic per event type, since they all converge on the same end state.
